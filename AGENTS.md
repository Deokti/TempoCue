# AGENTS.md

## Назначение проекта

TempoCue — локальный Windows-ассистент для League of Legends. Приложение получает состояние активного матча, преобразует его в собственную модель и детерминированно выбирает совет из Coach Pack. Текущие возможности и ближайший этап описаны в `README.md` и `docs/` — перед крупным изменением сверяйся с ними.

Главные качества проекта: корректность советов, предсказуемость поведения, возможность офлайн-тестирования, отзывчивый интерфейс и бережное отношение к данным игроков.

## Технологии и структура

- Используется C# с nullable reference types и implicit usings, SDK закреплён в `global.json`.
- `src/TempoCue.Core` — доменная модель, Coach Packs, проверка их данных и детерминированный движок правил.
- `src/TempoCue.Riot` — HTTP-доступ к Riot Live Client Data API, DTO и преобразование внешнего JSON в модели Core.
- `src/TempoCue.App` — WPF-интерфейс, локализация, настройки и сборка компонентов приложения.
- `tests/*` — тестовые проекты xUnit, соответствующие производственным проектам.
- `docs/` — границы версий, ручные сценарии проверки и источники знаний для Coach Packs.

## Архитектурные границы

- `docs/architecture.md` — канонический документ архитектуры. Перед новой функцией определи владельца поведения, поток данных и допустимые зависимости по этому документу.
- Текущее направление зависимостей: `TempoCue.Application -> TempoCue.Core`, `TempoCue.Riot -> TempoCue.Application/TempoCue.Core`, `TempoCue.App -> TempoCue.Application/TempoCue.Riot/TempoCue.Core`. Граф объектов активного матча создаётся в `App.OnStartup`; остальные функции переходят к этой схеме постепенно по `docs/architecture.md`.
- `TempoCue.Core` не должен зависеть от WPF, `TempoCue.App`, Riot DTO, HTTP или деталей отображения. Доменная логика должна работать без запущенной игры и интерфейса.
- `TempoCue.Riot` не должен зависеть от WPF или `TempoCue.App`. Изолируй формат Riot API в DTO и преобразователях; не распространяй внешние DTO в Core и UI.
- В `TempoCue.App` оставляй представление и координацию, специфичную для UI. Новые правила выбора советов, определения матчапа и интерпретации состояния размещай в Core, межсистемные сценарии — в целевом Application, а разбор Riot JSON — в Riot.
- Не добавляй новый слой, фреймворк, глобальный singleton или абстракцию только «на будущее». Вводи их при наличии конкретной границы, нескольких реализаций или проверяемой пользы.
- Не выполняй масштабную миграцию существующего WPF-кода, например на MVVM-фреймворк, в рамках несвязанной задачи. При росте окна извлекай самостоятельную логику небольшими проверяемыми шагами.
- Новые самостоятельные экраны создавай отдельными View/ViewModel, не расширяй ими `MainWindow.xaml`. Новый сценарий, координирующий Core и внешний эффект, выноси в целевой слой `TempoCue.Application` согласно плану постепенного перехода.
- Создание реализаций инфраструктуры разрешено в composition root (`App.OnStartup`), но не внутри View, ViewModel и доменных сервисов.
- Осознанное изменение архитектурного правила фиксируй ADR в `docs/adr/` и синхронизируй с `docs/architecture.md`.

## Правила реализации

- Сохраняй детерминизм движка: одинаковый Coach Pack и `MatchState` должны давать одинаковый результат. При равном приоритете правило выбора должно оставаться стабильным.
- Проверяй недоверенные данные на границе системы. После успешного преобразования Core должен получать валидные, осмысленные модели.
- При неоднозначных данных не угадывай критичное состояние. Безопасный результат `null`/«совет не определён» предпочтительнее случайного матчапа или неверного совета.
- Сетевые и длительные операции выполняй асинхронно, не блокируя UI-поток. Поддерживай `CancellationToken`, когда операция может быть отменена или живёт дольше одного действия пользователя.
- Для HTTP используй внедряемый `HttpClient`/обработчик, чтобы сценарий можно было проверить без реального матча и сети. Корректно освобождай владеющие ресурсами объекты.
- Не скрывай ошибки пустыми `catch`. Разделяй ожидаемое отсутствие активного матча и настоящие ошибки данных или приложения; пользователю показывай понятное состояние, а для диагностики сохраняй достаточный контекст без персональных данных.
- Предпочитай небольшие типы и методы с одной ясной ответственностью. Имена типов, методов и переменных должны выражать предметный смысл, а не механизм реализации.
- Соблюдай существующий стиль C#: file-scoped namespaces, PascalCase для типов и публичных членов, camelCase для локальных переменных и параметров, `_camelCase` для приватных полей.
- Не подавляй nullable-предупреждения оператором `!` без доказанного инварианта. Используй явную проверку входных значений и подходящие типы.
- Не добавляй новую production-зависимость и не обновляй целевой фреймворк без явного согласования с пользователем. Сначала оцени стандартную библиотеку и уже используемые зависимости.

## WPF и локализация

- Пользовательские операции не должны подвешивать окно; обновляй WPF-элементы только из UI-потока.
- Не помещай доменную или сетевую логику в обработчики событий. Обработчик координирует действие и обновляет представление, а проверяемая логика живёт в соответствующем проекте.
- Все видимые пользователю элементы интерфейса добавляй через стабильные ключи ресурсов в английский `Strings.resx` и русский `Strings.ru.resx`. Не оставляй новый UI-текст захардкоженным в XAML или C#.
- Текст советов и метаданные Coach Pack не относятся к ресурсам интерфейса. Автор набора сам определяет язык его содержимого; приложение локализует только собственные элементы управления и системные состояния.
- При добавлении или переименовании ключа обновляй обе локали и проверяй переключение языка без перезапуска. Английский остаётся резервным языком.
- Сохраняй доступность элементов: осмысленные подписи, предсказуемый keyboard focus и достаточный контраст. Декоративные изменения не должны ухудшать читаемость состояния матча.

## Coach Packs и данные Riot

- Coach Pack — входные данные, а не исполняемый код. Проверяй версию схемы, обязательные поля, диапазоны, уникальность ID и противоречивые условия до передачи правил движку.
- Изменение формата Coach Pack требует тестов загрузчика и решения по совместимости. Не меняй смысл существующего поля молча; при несовместимом формате увеличивай версию схемы и документируй переход.
- Для совета сохраняй источник, патч и ограничения применимости. Игровые рекомендации должны быть пересказом с указанием источника, а не большой дословной копией чужого материала.
- При обновлении Coach Pack синхронизируй JSON, относящуюся к нему документацию в `docs/coach-packs/` и тесты граничных состояний.
- Riot API может возвращать локализованные имена и неполные поля. Нормализацию выполняй в Riot mapper; Core использует стабильные внутренние значения.
- Снимки реального матча и диагностические данные могут содержать Riot ID. Перед сохранением в репозиторий, тестовый fixture, лог или документ заменяй идентификаторы вымышленными значениями. Не коммить секреты, токены и персональные данные.

## Тестирование

- Для новой доменной логики добавляй быстрые unit-тесты в соответствующий проект. Исправление дефекта по возможности начинай с теста, воспроизводящего дефект.
- Проверяй не только успешный путь, но и существенные границы: отсутствующие или неоднозначные данные, неверный JSON, диапазоны уровней, конфликтующие предметы, отмену и ошибки HTTP.
- Тесты Riot должны использовать сохранённый обезличенный JSON или подставной `HttpMessageHandler`; они не должны требовать запущенную League of Legends, интернет или Riot API key.
- WPF-тесты, создающие элементы интерфейса, запускай в STA-потоке и освобождай созданные окна. Избегай тестов, зависящих от задержек и состояния компьютера.
- Тест должен проверять наблюдаемое поведение. Не привязывай его к приватной реализации без необходимости.

## Рабочий процесс

1. Перед изменением прочитай затрагиваемый код, тесты и релевантные документы. Не делай выводы только по имени файла.
2. Сохраняй задачу узкой. Не исправляй несвязанные проблемы и не форматируй посторонние файлы.
3. Учитывай незакоммиченные изменения пользователя и не перезаписывай их.
4. После изменения сначала запускай целевые тесты, затем полную проверку решения, если среда это позволяет:

   ```powershell
   dotnet restore
   dotnet build TempoCue.sln --no-restore
   dotnet test TempoCue.sln --no-build
   ```

5. Если проверку выполнить нельзя, явно укажи, что именно не запускалось и почему. Не заявляй об успешной проверке без фактического запуска.
6. При изменении поведения, настройки, формата данных или архитектурной границы обновляй `README.md` и/или соответствующий файл в `docs/`. Для значимого архитектурного решения добавляй ADR.
7. При создании коммита следуй `docs/commits.md`: Conventional Commits, английские `type`/`scope` и русское описание результата.

## Критерии готовности

Изменение завершено, когда:

- соблюдены зависимости между Core, Riot и App;
- внешние и пользовательские данные корректно проверяются;
- новый пользовательский текст локализован на русский и английский;
- добавлены или обновлены тесты для изменённого поведения;
- решение собирается и релевантные тесты проходят;
- документация соответствует поведению;
- в diff нет секретов, реальных Riot ID, сгенерированных `bin/`/`obj/` и несвязанных изменений.
