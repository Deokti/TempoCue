# Правила оформления коммитов

TempoCue использует [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/). Эти правила делают историю понятной человеку и пригодной для автоматического формирования changelog и определения характера релиза.

## Формат

```text
<type>(<scope>)!: <description>

[необязательное тело]

[необязательные сноски]
```

Для обычного коммита обязательны `type`, `scope` и `description`. Знак `!`, тело и сноски добавляются только при необходимости.

Пример:

```text
feat(riot): добавить запись снимков активного матча
```

## Язык и написание

- `type` и `scope` пишутся на английском строчными буквами.
- Составной scope записывается в `kebab-case`, например `coach-pack`.
- Краткое описание, тело и пояснения к критическим изменениям пишутся на русском языке.
- Описание начинается со строчной буквы, формулируется как действие в неопределённой форме: `добавить`, `исправить`, `выделить`, `обновить`.
- В конце заголовка точка не ставится.
- Заголовок описывает результат коммита, а не процесс работы. Не используй `изменения`, `правки`, `update`, `WIP`, `починить что-то` и похожие неопределённые формулировки.
- Заголовок должен оставаться кратким и читаться без просмотра diff. Если причины и ограничения не помещаются, добавь тело.

## Типы

| Тип | Когда использовать | Пример |
| --- | --- | --- |
| `feat` | Новая возможность или новое наблюдаемое поведение | `feat(settings): добавить выбор темы` |
| `fix` | Исправление неправильного поведения | `fix(match): не выбирать противника при неоднозначной позиции` |
| `docs` | Изменения только в документации и инструкциях | `docs(architecture): описать адаптер хранения снимков` |
| `refactor` | Перестройка кода без изменения поведения | `refactor(ui): выделить представление текущего матча` |
| `test` | Добавление или изменение только тестов | `test(coaching): проверить равный приоритет правил` |
| `perf` | Измеримое улучшение производительности без новой функции | `perf(riot): сократить выделения при разборе снимка` |
| `build` | Система сборки, SDK и зависимости | `build(deps): обновить xunit` |
| `ci` | Конфигурация и сценарии CI | `ci(tests): запускать тесты WPF на Windows` |
| `chore` | Техническое обслуживание, не подходящее под более точный тип | `chore(repo): удалить устаревшие артефакты` |
| `style` | Только форматирование, пробелы или стиль без изменения поведения | `style(core): выровнять форматирование файлов` |
| `revert` | Отмена одного или нескольких прежних коммитов | `revert(ui): отменить новый макет главной страницы` |

`feat` используется только для новой функциональности, а `fix` — только для исправления дефекта. `refactor` не должен скрывать изменение поведения. `chore` не служит универсальной заменой более точному типу.

Если изменение естественно распадается на несколько типов, по возможности раздели его на несколько самостоятельных коммитов.

## Scope

Scope называет одну основную область ответственности, а не перечисляет все изменённые каталоги.

Основные scope TempoCue:

| Scope | Область |
| --- | --- |
| `app` | запуск приложения, composition root и общая координация |
| `core` | общая доменная модель и инварианты |
| `match` | состояние матча и определение участников/матчапа |
| `coaching` | выбор и представление тренерских советов |
| `coach-pack` | схема, загрузка и содержимое Coach Packs |
| `riot` | Live Client Data API, DTO и mapper |
| `ui` | WPF Views, ViewModels, навигация и стили |
| `settings` | пользовательские настройки |
| `i18n` | локализация и языковые ресурсы |
| `architecture` | архитектурные правила и ADR |
| `docs` | общая документация, не относящаяся к более точной области |
| `git` | правила истории, hooks и настройки репозитория |
| `tests` | общая тестовая инфраструктура |
| `deps` | обновление зависимостей |

Список не закрытый: новый scope разрешён, если существующие не выражают владельца изменения. Не создавай новый синоним уже существующей области. Для новых scope используй строчные буквы и `kebab-case`.

## Тело коммита

Тело добавляется, если заголовка недостаточно для понимания решения. Оно отвечает прежде всего на вопросы «зачем?» и «какие ограничения учтены?», не пересказывает построчно diff.

Заголовок и тело разделяются пустой строкой:

```text
fix(riot): различать завершённый матч и ошибку JSON

Отсутствие ответа после выхода из игры является ожидаемым состоянием.
Ошибка разбора по-прежнему отображается как диагностическая проблема.
```

## Сноски и ссылки

Сноски отделяются от тела пустой строкой и используют формат Git trailer:

```text
Refs: #42
Closes: #57
Reviewed-by: Имя
```

Не добавляй вымышленные номера задач. Если коммит не связан с issue, сноска не нужна.

## Критические изменения

Изменение, нарушающее обратную совместимость публичного контракта, формата Coach Pack, сохранённых настроек или записанных снимков, обозначается `!` перед двоеточием. В сноске обязательно объясняется, что сломано и как перейти:

```text
feat(coach-pack)!: изменить формат условий предметов

Новая модель позволяет выражать альтернативные наборы предметов.

BREAKING CHANGE: Coach Packs schemaVersion 1 больше не загружаются;
перенесите requiredItemIds в itemConditions и установите schemaVersion 2.
```

Нельзя скрывать несовместимое изменение под обычным `feat`, `refactor` или `chore`.

## Атомарность коммита

- Один коммит выражает одно законченное намерение и по возможности остаётся собираемым и проверяемым.
- В коммит не входят случайное форматирование, временные файлы и несвязанные исправления.
- Производственный код и необходимые для него тесты/документация могут находиться в одном коммите: тип выбирается по основному пользовательскому намерению.
- Если сообщение требует союзов вроде «добавить X и исправить несвязанное Y», изменения нужно разделить.
- Не делай отдельный коммит только для исправления опечатки, которую можно включить в ещё не завершённый локальный коммит, если история ещё не опубликована.
- Опубликованную общую историю не переписывай без явного согласования.

## Примеры

Хорошо:

```text
feat(coaching): добавить совет для нового power spike
fix(i18n): обновлять журнал после смены языка
refactor(ui): вынести экран матча из главного окна
docs(git): описать правила оформления коммитов
test(riot): проверить ответ без активного игрока
```

Плохо:

```text
Добавить новый экран
feat: правки
fix(ui): фикс бага.
chore(core): WIP
feat(ui,riot): добавить экран и переделать клиент
```

Причины: отсутствует conventional-заголовок или обязательный scope, описание неопределённое, используется неправильная форма, перечислено несколько областей либо смешаны разные намерения.

## Проверка перед коммитом

1. `git status --short` содержит только ожидаемые файлы.
2. `git diff --cached --check` не сообщает об ошибках.
3. Staged diff выражает одно намерение и не содержит секретов, персональных данных, `bin/` или `obj/`.
4. Выбран точный тип и один основной scope.
5. Заголовок соответствует шаблону и описывает результат.
6. Выполнены релевантные сборка и тесты либо явно зафиксирована причина, почему они не запускались.

## Состояние истории на момент принятия правил

На 9 августа 2026 года все 12 существующих коммитов соответствуют базовому синтаксису Conventional Commits:

- 7 `feat`;
- 2 `docs`;
- 2 `refactor`;
- 1 `chore`.

История уже использует русские описания и предметные scope: `app`, `coaching`, `match`, `riot`, `branding`, `i18n`, `ui`, `settings`, `docs`, `code` и `AGENTS`. Последний вариант остаётся историческим исключением по регистру. Существующие сообщения не переписываются; для новых коммитов scope нормализуются в нижний регистр и выбираются по таблице выше.
