# Собственная модель распознавания: план программы

Решение принято 23 августа 2026 года по итогам эксперимента DeeperLeague.

**Этот документ — точка входа.** Любая новая сессия работы (включая новый чат с
ассистентом) начинается с чтения этого файла, раздела «Потолок собственной
модели» в `vision-improvement-plan.md` и записей TC-003/TC-004 в
`known-issues.md`. Этого достаточно, чтобы продолжить без пересказа истории.
Обратное правило такое же строгое: решение, принятое в разговоре, не существует,
пока не записано сюда или в связанные документы.

Переписку прошлой сессии передать нельзя — она не читается новой. Кроме
документов контекст несёт история коммитов: тела написаны так, чтобы объяснять
причину решения, а не перечислять изменения. `git log` по каталогу
`src/TempoCue.Vision` восстанавливает ход рассуждений лучше любого пересказа.

Внедрение готовой модели — тоже новая сессия, уже в этом репозитории. Отдельного
разбора она не потребует: шов `IMinimapFrameAnalyzer` существует, а
`TempoCue.Vision.DeeperLeague` служит рабочим примером подключения ONNX-модели.
Задача сводится к повторению этого примера и приёмке по разделу ниже.

## На чём стоит решение

Измерено, а не предположено (`ReplayInspect --ceiling`, корпус из 12 кадров):

| | Чемпионов | Доля |
|---|---|---|
| подтверждено конвейером | 44 | 73,3 % |
| пропущено без области сравнения — возьмёт детектор «где» | 6 | 10,0 % |
| пропущено с областью — нужно лучшее различение «кто» | 10 | 16,7 % |

Больная часть — различение похожих портретов: баллы пиксельного сравнения лежат
в узкой полосе `0,71`–`0,85`, где шум сопоставим с разницей между чемпионами.

## Архитектура: вложение, а не классификация

Классификатор на N чемпионов (путь DeeperLeague) замораживает набор классов в
весах: новый чемпион или перерисованный значок требуют переобучения. Эту цену мы
измерили — модель 13.14 не знает 9 новых чемпионов и теряет часть перерисованных.

Вместо этого сеть переводит вырез значка в **вектор** (embedding). Опознание —
сравнение с векторами, посчитанными из значков актуального Data Dragon:

- новый чемпион = посчитать один вектор, без переобучения;
- перерисованный значок = вектор пересчитывается сам;
- различение обученное, а не пиксельное — закрывает полосу `0,71`–`0,85`.

Полная схема двухступенчатая: лёгкий детектор отвечает «где значки», вложение
отвечает «кто это». Обе ступени закрывают свой класс пропусков из таблицы выше.

### Уточнения после внешнего исследования (23 августа 2026)

**Постановка точнее, чем «распознавание лиц».** Неизвестных личностей у нас
почти нет — состав из десяти известен из API. Зато сами классы динамические и
могут отсутствовать при обучении. Это **опознание по одному эталону с
динамической галереей и правом отказа**, и под такую постановку прямо
разрабатывались Prototypical Networks.

**Функция потерь: эпизодическая прототипная InfoNCE, не ArcFace и не triplet.**
Довод решающий и геометрический: при обучении ArcFace класс представлен
*обучаемым весом классификатора*, а у нас в бою класс представлен *вектором
картинки из Data Dragon*, которой при обучении не было. Обучающая задача обязана
совпадать с боевой, иначе мы оптимизируем не то. В эпизоде берутся десять
чемпионов, чистые значки Data Dragon — прототипы, испорченные варианты —
запросы, softmax считается прямо по косинусу. ArcFace остаётся кандидатом на
вспомогательное слагаемое, но выбирается только по точности на **невиданных**
чемпионах.

**Косинус сам по себе ничего не чинит.** Полосу `0,71`–`0,85` лечит не смена
метрики, а обученная функция, выбрасывающая изменчивость, не относящуюся к
личности: субпиксельный сдвиг, интерполяцию, кольцо, свечение, перекрытие.

**Детектор — карта центров, шаг 4.** Значок диаметром 25 пикселей занимает около
шести клеток карты 80×80; при шаге 8 остаётся три, и близкие значки при
перекрытии сливаются. Голова ширины и высоты не нужна вовсе: размер известен.
Сегментация отвергнута по той же причине — два перекрытых круга дают одну
связную область, а у карты центров остаются две вершины.

**Кольцо команды не должно быть признаком личности.** Детектору оно полезно —
хороший признак «здесь значок». Вложению — опасно: в синтетике легко возникает
случайная связь «чемпион ↔ сторона», и сеть возьмёт этот дешёвый обходной путь
вместо портрета. Кольцо рандомизируется независимо от чемпиона.

**Прототип усредняется по нескольким отрисовкам.** Не один вектор с одного
значка, а среднее от 4–16 канонических вариантов: субпиксельные фазы, варианты
кольца, разные ресемплеры. Это по-прежнему подключение нового чемпиона без
обучения — миллисекунды на PNG.

**Отказ как третий исход.** При перекрытии в 90 % оставшихся пикселей может
физически не хватать для различения. Требовать ответ в такой ситуации неверно;
нужна маленькая голова качества и решение вида «уверен / доказательств
недостаточно». Это ровно случай Tristana за Blitzcrank.

**Время — самый дешёвый инструмент против перекрытий.** Закрытый на 80 %
чемпион через 200 мс может быть открыт. Накопление решения по нескольким кадрам
дешевле, чем сложные архитектуры для частично видимых объектов, и у нас уже есть
для этого механизм — `ParticipantVisibilityTracker`.

**Главный эксперимент всей программы.** Обучить на 130–140 чемпионах, 30–40
никогда не показывать, а при проверке дать только их чистые прототипы. Если
невиданные чемпионы не опознаются — обещание «новый чемпион без переобучения» не
выполнено, и вложение осталось замаскированным классификатором на 170 классов.

**Опасность, которую надо проверить до всего остального.** Не доказано, что
портрет из Data Dragon — тот же визуальный источник, что попадает на миникарту.
Наше пиксельное сравнение даёт до `0,94` на хороших значках, что говорит о
близости, но не о тождестве. Отдельный инструмент «сверки отрисовки» должен
перебирать масштаб, субпиксельный сдвиг, ресемплер, толщину кольца, размытие,
гамму и режим альфа-канала, отыскивая параметры, минимизирующие расхождение с
настоящим вырезом. Это превращает «синтетика почему-то другая» в измеримые
параметры.

**Проверка домена одним классификатором.** Если маленькая сеть легко отличает
синтетический вырез от настоящего, домены расходятся. Дёшево и находит грубые
систематические артефакты до того, как в них упрётся обучение.

**Чего не рандомизировать.** Искажения объектива, хроматические аберрации, шум
матрицы и артефакты JPEG приходят из литературы про настоящие камеры. У нас
цифровой захват экрана, и обучать инвариантности к помехе, которой в production
нет, — вред. Тот же принцип, что и везде в проекте: не добавлять неизмеренное.

## Как обучается модель — для читателя без опыта

Модель — функция с миллионами настраиваемых чисел (весов). Обучение — показ
примеров с известным ответом: за каждую ошибку веса чуть сдвигаются в сторону
правильного ответа. Всё остальное — организация этого процесса.

Короткий словарь:

- **датасет** — набор примеров с ответами (кадр + где на нём значки);
- **разметка** — сами ответы; у нас бесплатна, потому что кадры синтетические;
- **аугментация** — искусственное разнообразие: сдвиги, шум, свечение;
- **эпоха** — один проход обучения по всему датасету;
- **инференс** — применение обученной модели к новому кадру;
- **ONNX** — переносимый формат готовой модели; его читает приложение;
- **вложение (embedding)** — вектор чисел, описывающий картинку так, что
  похожие картинки дают близкие векторы.

Разделение труда: код генератора данных, обучения и приёмки пишет ассистент.
За игроком — решения, тренировочные матчи, кадры для корпуса и запуск обучения
(одна команда).

## Машины

Доступны две, и роли у них разные.

| | Разработка | Вторая машина |
|---|---|---|
| процессор | Ryzen 7 3700X, 3,6 ГГц | Ryzen 7 9800X3D, 4,7 ГГц |
| видеокарта | RTX 3070 Ti | RTX 5070 Ti, 16 ГБ |
| память | 80 ГБ | 64 ГБ |
| система | Windows 10 | Windows 11 |

**Обучение — на второй машине.** Выигрыш есть и он бесплатный, но ожидания
должны быть трезвыми: модели такого размера учатся часами на любой из двух, и
переезд экономит часы, а не дни. Узкое место программы — качество генератора
данных и число итераций, а не скорость видеокарты. Объём видеопамяти здесь тоже
не различает машины: восьми гигабайт для наших размеров хватает с запасом.

Существеннее другое: генерация синтетического датасета — работа процессора
(композиция изображений), и здесь разрыв между 3700X и 9800X3D больше, чем между
видеокартами.

Две вещи проверить до начала, а не предполагать: поддержку RTX 50-й серии
(Blackwell) в стабильной сборке PyTorch с нужной версией CUDA, и целесообразность
WSL2 вместо Windows напрямую — многопроцессная загрузка данных в PyTorch под
Windows медленнее.

**Живых проверок на второй машине не будет** — League на ней недоступна. Значит
все замеры в матче, кадры для корпуса и проверки уведомлений идут только на
машине разработки, и это постоянное ограничение программы, а не временное
неудобство.

Что вторая машина всё же даёт помимо обучения: генерацию датасета и **офлайновые
замеры** — `ReplayInspect --timing`, `--soak`, `--ceiling` работают на
сохранённых кадрах и игры не требуют. Прогон `--timing` там покажет, как
стоимость кадра зависит от процессора, и это единственный доступный нам способ
проверить, не подогнаны ли умолчания под одну конфигурацию.

Следствие для умолчаний: они настраиваются по одной живой машине. Значит опираться
они должны на величины, которые от машины не зависят, — окно подтверждения
видимости в 600 мс и долю логических процессоров, — а не на абсолютные
миллисекунды, измеренные здесь.

## Данные

Обучение — на **синтетике**, как у DeeperLeague, но генератор наш и живой:

- фоны миникарты + значки из актуального Data Dragon, командные кольца,
  перекрытия, свечение отзыва/телепорта, пинги, разные масштабы;
- разметка получается бесплатно — позиции значков известны генератору;
- при патче Riot датасет перегенерируется одной командой. Это решает проблему
  устаревания структурно, а не заплатками.

**Корпус replay-кадров — только приёмка, никогда не обучение.** Обучать на нём —
экзамен по шпаргалке: реальные кадры должны оставаться независимой проверкой.
Урок проверки значков в силе: синтетика систематически отличается от игры
(кольцо — часть того, что модель учит), поэтому финальная оценка — только по
корпусу через существующие `ReplayInspect --compare` и `--ceiling`.

## Разделение репозиториев

Обучение живёт в **отдельном приватном репозитории** (рабочее имя
`tempocue-vision-model`): Python/PyTorch, генератор датасета, скрипты обучения и
экспорта. Причины: другой стек, крупные артефакты, лицензионная гигиена.

Граница между репозиториями — **один артефакт**: файл ONNX плюс файл
соответствия. Продукт подключает его как сейчас DeeperLeague: каталог в
`models/`, реализация `IMinimapFrameAnalyzer`. Приёмка выполняется в этом
репозитории существующими инструментами — модельный репозиторий ничего не знает
о продукте, продукт ничего не знает об обучении.

Собственные веса можно хранить в Releases модельного репозитория: в отличие от
чужих, они наши.

## Приёмка модели: договор между репозиториями

Модель принимается **в этом репозитории**, существующими инструментами и по
существующему корпусу. Модельный репозиторий отдаёт только файлы ONNX; решение
«годится или нет» принимается здесь.

Порядок:

```powershell
dotnet run --project tools/ReplayInspect -c Release -- --compare tests/TempoCue.Vision.Tests/ReplayCorpus
dotnet run --project tools/ReplayInspect -c Release -- --ceiling tests/TempoCue.Vision.Tests/ReplayCorpus
dotnet run --project tools/ReplayInspect -c Release -- --timing tests/TempoCue.Vision.Tests/ReplayCorpus
```

С чем сравнивается (корпус из 12 кадров, 60 размеченных чемпионов):

| Распознаватель | Верных | Ложных |
|---|---|---|
| наш конвейер | 44 | 1 |
| DeeperLeague | 48 | 5 |
| своя модель | цель ниже | |

Порог допуска:

1. **Ложных не больше одного.** Полнота, купленная ложными подтверждениями, нам не
   нужна: игрок теряет доверие к уведомлению быстрее, чем радуется найденному.
2. **Верных заметно больше 48** — с оговоркой ниже про статистику.
3. **Стоимость кадра не больше 125 мс при двух потоках.** Прежняя формулировка
   «300 мс» смешивала две разные величины: 300 мс — предел задержки, при котором
   не рвётся цепочка подтверждения видимости, но пропускную способность задаёт
   интервал разбора. При 300 мс на кадр система физически выдаёт 3,3 кадра в
   секунду вместо восьми.
4. **Ни один из шестидесяти уже подтверждённых чемпионов не потерян.** Замена,
   которая берёт новых и теряет старых, — не улучшение.

Потолок для ориентира: один пропуск (Tristana за Blitzcrank в кадре 12) не
восстановим в принципе — виден только ободок кольца. Значит предел — 59 из 60.

### Двенадцать кадров не доказывают разницу

Внешнее исследование сделало замечание, которое обесценивает часть наших выводов
и должно быть записано целиком.

Для 44 из 60 доверительный интервал Вильсона составляет **61,0–82,9 %**, для 48
из 60 — **68,2–88,2 %**. Интервалы перекрываются почти полностью. Разница в
четыре чемпиона на такой выборке **не доказывает превосходства** DeeperLeague над
нашим конвейером, хотя мы всё это время говорили о ней как об установленной.

Дальше хуже. Оба распознавателя прогонялись по одним и тем же объектам, поэтому
сравнение обязано быть **парным**: значение имеет не 44 против 48, а таблица
«кого взял только один и кого только другой». Агрегированные числа этого не
показывают.

И шестьдесят чемпионов — не шестьдесят независимых наблюдений: пятеро в одном
кадре делят фон, патч, состояние отрисовки и часто саму причину ошибки.
Доверительные интервалы для итогового сравнения нужно строить бутстрапом по
матчам, а не по значкам.

Практический вывод: **корпус нужно расширять**, и до этого числа приёмки следует
читать как ориентир, а не как доказательство. Порог «заметно больше 48» означает
разницу, переживающую парное сравнение, а не арифметическое превосходство.

### Корпус сейчас — набор для разработки, а не для приёмки

Это вторая поправка, и она к моему же тексту. Двенадцать кадров уже перестали
быть слепой выборкой: их разбор — шесть пропусков без области, десять с областью,
конкретные пары Sett/MasterYi и Ziggs/Teemo — **уже повлиял на выбор
архитектуры**. Это утечка информации в разработку, даже без единого шага
градиентного спуска по этим изображениям.

Правильное деление:

| Набор | Назначение | Можно ли смотреть |
|---|---|---|
| синтетика (обучение) | обучение | да |
| синтетика (валидация) | поиск ошибок, регрессии | да |
| нынешние 12 кадров | разработка: пороги, генератор, ablations | да |
| **новый слепой корпус** | итоговая приёмка | **только после заморозки** |

Слепой корпус собирается из **других матчей и сессий**, желательно на другом
патче, и не открывается до момента, когда обучение и пороги заморожены.
Дообучение на приёмочном наборе с последующим называнием его приёмочным — то же
самое, что экзамен по собственной шпаргалке.

Живая проверка после корпуса обязательна и только на машине разработки:
тренировочный матч, доля процессора в диспетчере задач, задержка уведомлений.
Корпус не заменяет её — в нём двенадцать кадров, а не матч.

## Лицензии

Обучение — на чистом PyTorch, **без Ultralytics**: её AGPL-3.0 распространяется
на производные веса, и мы уже держим DeeperLeague вне репозитория именно поэтому.
Значки Riot используются локально; вопрос публикации датасета отложен до решения
о лицензии TempoCue, как и остальные вопросы распространения.

## Требование к интеграции — урок TC-003

Настройка «Потоки распознавания карты» обязана доходить до каждого рантайма,
который создаёт потоки. OpenCV и ONNX Runtime оба заводили собственные пулы по
числу ядер, и расход процессора не зависел от настройки, пока это не было
ограничено явно. Любой новый рантайм проверяется на это в первую очередь.

## Чего модель не изменит

Постоянная часть расхода процессора — около 9 % — от распознавания не зависит
(приём кадров, нормализация, оверлей, опрос Riot). Модель уменьшает только
переменную часть. Отдельная цель «сократить постоянную часть» остаётся в
TC-003 и от модели не зависит.

## Ступени работ

1. **Каркас модельного репозитория.** Создаёт игрок на GitHub (приватный),
   ассистент наполняет: структура, зависимости, README с этим же контекстом.
2. **Генератор синтетики.** Без ML вообще; результат проверяется глазами:
   сгенерированный кадр должен быть неотличим по устройству от настоящего.
   Это самая ценная часть программы — качество данных решает больше архитектуры.
3. **Крошечный детектор «где».** Цель — не качество, а обкатка полного цикла:
   данные → обучение → ONNX → приёмка по корпусу в основном репозитории.
4. **Честное сравнение.** Три участника на одном корпусе: наш конвейер,
   DeeperLeague, своя модель. Решения — только по этим числам.
5. **Вложение «кто».** Обучение на парах «тот же / другой чемпион»; сравнение с
   векторами из Data Dragon; приёмка та же.
6. **Гибрид в приложении.** За настройкой, рядом с экспериментальным режимом;
   штатный путь остаётся по умолчанию до подтверждения на живых матчах.

Между ступенями — фиксация результата в документах. Ступень без записанного
результата считается несделанной.
