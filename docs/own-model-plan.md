# Собственная модель распознавания: план программы

Решение принято 23 августа 2026 года по итогам эксперимента DeeperLeague.

**Этот документ — точка входа.** Любая новая сессия работы (включая новый чат с
ассистентом) начинается с чтения этого файла, раздела «Потолок собственной
модели» в `vision-improvement-plan.md` и записей TC-003/TC-004 в
`known-issues.md`. Этого достаточно, чтобы продолжить без пересказа истории.
Обратное правило такое же строгое: решение, принятое в разговоре, не существует,
пока не записано сюда или в связанные документы.

## На чём стоит решение

Измерено, а не предположено (`ReplayInspect --ceiling`, корпус из 12 кадров):

| | Чемпионов | Доля |
|---|---|---|
| подтверждено конвейером | 44 | 73,3 % |
| пропущено без области сравнения — возьмёт детектор «где» | 6 | 10,0 % |
| пропущено с областью — нужно лучшее различение «кто» | 10 | 16,7 % |

Больная часть — различение похожих портретов: баллы пиксельного сравнения лежат
в узкой полосе `0,71`–`0,85`, где шум сопоставим с разницей между чемпионами.

## Архитектура: вложение, а не классификация

Классификатор на N чемпионов (путь DeeperLeague) замораживает набор классов в
весах: новый чемпион или перерисованный значок требуют переобучения. Эту цену мы
измерили — модель 13.14 не знает 9 новых чемпионов и теряет часть перерисованных.

Вместо этого сеть переводит вырез значка в **вектор** (embedding). Опознание —
сравнение с векторами, посчитанными из значков актуального Data Dragon:

- новый чемпион = посчитать один вектор, без переобучения;
- перерисованный значок = вектор пересчитывается сам;
- различение обученное, а не пиксельное — закрывает полосу `0,71`–`0,85`.

Полная схема двухступенчатая: лёгкий детектор отвечает «где значки», вложение
отвечает «кто это». Обе ступени закрывают свой класс пропусков из таблицы выше.

## Как обучается модель — для читателя без опыта

Модель — функция с миллионами настраиваемых чисел (весов). Обучение — показ
примеров с известным ответом: за каждую ошибку веса чуть сдвигаются в сторону
правильного ответа. Всё остальное — организация этого процесса.

Короткий словарь:

- **датасет** — набор примеров с ответами (кадр + где на нём значки);
- **разметка** — сами ответы; у нас бесплатна, потому что кадры синтетические;
- **аугментация** — искусственное разнообразие: сдвиги, шум, свечение;
- **эпоха** — один проход обучения по всему датасету;
- **инференс** — применение обученной модели к новому кадру;
- **ONNX** — переносимый формат готовой модели; его читает приложение;
- **вложение (embedding)** — вектор чисел, описывающий картинку так, что
  похожие картинки дают близкие векторы.

Разделение труда: код генератора данных, обучения и приёмки пишет ассистент.
За игроком — решения, тренировочные матчи, кадры для корпуса и запуск обучения
(одна команда).

## Машины

Доступны две, и роли у них разные.

| | Разработка | Вторая машина |
|---|---|---|
| процессор | Ryzen 7 3700X, 3,6 ГГц | Ryzen 7 9800X3D, 4,7 ГГц |
| видеокарта | RTX 3070 Ti | RTX 5070 Ti, 16 ГБ |
| память | 80 ГБ | 64 ГБ |
| система | Windows 10 | Windows 11 |

**Обучение — на второй машине.** Выигрыш есть и он бесплатный, но ожидания
должны быть трезвыми: модели такого размера учатся часами на любой из двух, и
переезд экономит часы, а не дни. Узкое место программы — качество генератора
данных и число итераций, а не скорость видеокарты. Объём видеопамяти здесь тоже
не различает машины: восьми гигабайт для наших размеров хватает с запасом.

Существеннее другое: генерация синтетического датасета — работа процессора
(композиция изображений), и здесь разрыв между 3700X и 9800X3D больше, чем между
видеокартами.

Две вещи проверить до начала, а не предполагать: поддержку RTX 50-й серии
(Blackwell) в стабильной сборке PyTorch с нужной версией CUDA, и целесообразность
WSL2 вместо Windows напрямую — многопроцессная загрузка данных в PyTorch под
Windows медленнее.

**Вторая машина ценна и как испытательная.** Она сильно быстрее по процессору, а
TempoCue считает именно на нём: замеры TC-003 на ней дадут другие числа, и это
проверит, насколько наши умолчания разумны за пределами одной конфигурации.

## Данные

Обучение — на **синтетике**, как у DeeperLeague, но генератор наш и живой:

- фоны миникарты + значки из актуального Data Dragon, командные кольца,
  перекрытия, свечение отзыва/телепорта, пинги, разные масштабы;
- разметка получается бесплатно — позиции значков известны генератору;
- при патче Riot датасет перегенерируется одной командой. Это решает проблему
  устаревания структурно, а не заплатками.

**Корпус replay-кадров — только приёмка, никогда не обучение.** Обучать на нём —
экзамен по шпаргалке: реальные кадры должны оставаться независимой проверкой.
Урок проверки значков в силе: синтетика систематически отличается от игры
(кольцо — часть того, что модель учит), поэтому финальная оценка — только по
корпусу через существующие `ReplayInspect --compare` и `--ceiling`.

## Разделение репозиториев

Обучение живёт в **отдельном приватном репозитории** (рабочее имя
`tempocue-vision-model`): Python/PyTorch, генератор датасета, скрипты обучения и
экспорта. Причины: другой стек, крупные артефакты, лицензионная гигиена.

Граница между репозиториями — **один артефакт**: файл ONNX плюс файл
соответствия. Продукт подключает его как сейчас DeeperLeague: каталог в
`models/`, реализация `IMinimapFrameAnalyzer`. Приёмка выполняется в этом
репозитории существующими инструментами — модельный репозиторий ничего не знает
о продукте, продукт ничего не знает об обучении.

Собственные веса можно хранить в Releases модельного репозитория: в отличие от
чужих, они наши.

## Лицензии

Обучение — на чистом PyTorch, **без Ultralytics**: её AGPL-3.0 распространяется
на производные веса, и мы уже держим DeeperLeague вне репозитория именно поэтому.
Значки Riot используются локально; вопрос публикации датасета отложен до решения
о лицензии TempoCue, как и остальные вопросы распространения.

## Требование к интеграции — урок TC-003

Настройка «Потоки распознавания карты» обязана доходить до каждого рантайма,
который создаёт потоки. OpenCV и ONNX Runtime оба заводили собственные пулы по
числу ядер, и расход процессора не зависел от настройки, пока это не было
ограничено явно. Любой новый рантайм проверяется на это в первую очередь.

## Чего модель не изменит

Постоянная часть расхода процессора — около 9 % — от распознавания не зависит
(приём кадров, нормализация, оверлей, опрос Riot). Модель уменьшает только
переменную часть. Отдельная цель «сократить постоянную часть» остаётся в
TC-003 и от модели не зависит.

## Ступени работ

1. **Каркас модельного репозитория.** Создаёт игрок на GitHub (приватный),
   ассистент наполняет: структура, зависимости, README с этим же контекстом.
2. **Генератор синтетики.** Без ML вообще; результат проверяется глазами:
   сгенерированный кадр должен быть неотличим по устройству от настоящего.
   Это самая ценная часть программы — качество данных решает больше архитектуры.
3. **Крошечный детектор «где».** Цель — не качество, а обкатка полного цикла:
   данные → обучение → ONNX → приёмка по корпусу в основном репозитории.
4. **Честное сравнение.** Три участника на одном корпусе: наш конвейер,
   DeeperLeague, своя модель. Решения — только по этим числам.
5. **Вложение «кто».** Обучение на парах «тот же / другой чемпион»; сравнение с
   векторами из Data Dragon; приёмка та же.
6. **Гибрид в приложении.** За настройкой, рядом с экспериментальным режимом;
   штатный путь остаётся по умолчанию до подтверждения на живых матчах.

Между ступенями — фиксация результата в документах. Ступень без записанного
результата считается несделанной.
