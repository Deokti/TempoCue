# 0011. Видимость участника подтверждается последовательностью кадров

- Статус: принято
- Дата: 2026-08-21

## Контекст

Даже после подтверждения портрета OpenCV отдельный кадр остаётся шумным наблюдением. Башня,
тотем, пачка миньонов или портрет мёртвого участника способны на одном кадре получить похожий
балл. Немедленное превращение такого результата в состояние «чемпион виден» вызывает мерцание,
ложные события контроля карты и ошибочные уведомления о леснике.

Vision не знает участников Core и признака смерти из Live Client Data. WPF и оверлей не должны
самостоятельно принимать разные решения по одинаковому потоку кадров. Нужен один
детерминированный владелец временного состояния, проверяемый без League, Windows Graphics Capture
и OpenCV.

## Решение

- `TempoCue.Vision` публикует неизменяемое наблюдение одного кадра: распознанный чемпион,
  относительную сторону, уверенность, время и геометрию на канонической миникарте;
- App сопоставляет наблюдение с конкретным участником текущего матча, используя состав и стороны
  из Core;
- `ParticipantVisibilityTracker` в `TempoCue.Application` владеет временной стабилизацией и
  возвращает готовый снимок состояния участника;
- первое наблюдение переводит участника в `Confirming`, а `Visible` требует два последовательных
  обнаружения с интервалом не более 600 миллисекунд;
- после пропуска кадров подтверждённая видимость удерживается не более одной секунды, затем
  участник становится `NotVisible`; последнее подтверждённое время и нормализованные координаты
  сохраняются;
- участник, которого Live Client Data пометил мёртвым, исключается из ожидаемых наблюдений и не
  может оставаться видимым из-за статичного портрета смерти;
- WPF только отображает готовые состояния, а будущий сценарий контроля карты и оверлей должны
  потреблять тот же стабилизированный снимок, а не кандидатов отдельного кадра.

Начальные интервалы являются проверяемой политикой, а не свойством OpenCV. Их можно изменить по
результатам replay-последовательностей без замены захвата или распознавателя.

## Альтернативы

### Считать каждый подтверждённый OpenCV-портрет фактом

Минимальная задержка достигается ценой ложных вспышек на одном кадре. Для предупреждения о
леснике такая ошибка опаснее задержки примерно в четверть секунды.

### Хранить временное состояние внутри Vision

Vision пришлось бы знать идентификаторы участников, их смерть и жизненный цикл матча. Это
смешивает внешний адаптер изображения с прикладным состоянием и затрудняет смену OpenCV.

### Стабилизировать отдельно во ViewModel и оверлее

Два потребителя получили бы разные состояния и пороги. Такой код невозможно надёжно использовать
будущими сценариями контроля карты.

## Последствия

Положительные:

- одиночное ложное совпадение не становится видимостью участника;
- смерть и смена состава сбрасывают устаревшее состояние;
- координаты и последнее время обнаружения готовы для будущих событий появления и исчезновения;
- логика проверяется быстрыми тестами без изображения и Windows.

Ограничения:

- подтверждение добавляет около 250 миллисекунд при диагностической частоте четыре кадра в
  секунду;
- текущий replay одного кадра не проверяет временной трекер; для precision/recall по времени
  понадобится формат последовательности кадров с ручной разметкой;
- два наложившихся портрета и длительное ошибочное совпадение требуют дальнейшего улучшения
  распознавателя и набора hard negatives.
