# 0016. Сигналы наблюдения живут в наборах контроля карты

- Статус: принято
- Дата: 2026-08-27

## Контекст

Приложение умеет два вида подсказок о карте, и устроены они несопоставимо.

**Напоминания о нейтральных объектах** — восемь переносимых наборов
(`mapControl`): драконы, Личинки, Герольд, Барон и другие. Каждый набор
включается отдельно, у каждого правила есть сообщение, «почему сейчас», «что
дальше» и приоритет. Наборы редактируются, импортируются и обмениваются.

**Сигналы наблюдения** — появление вражеского лесника и пропажа мидера —
**зашиты в код**. Роль, событие, текст и приоритет заданы `switch`-выражением в
`MapAwarenessSignalPolicy` и строками локализации. Игрок не может ни отключить
их по отдельности, ни изменить формулировку, ни добавить свои.

Трекер видимости ролей не знает: он отдаёт «участник появился» или «участник
пропал», а роль берётся из состава матча. Значит доступна вся матрица **5 ролей
× 2 события = 10 сигналов**, из которых подключены два.

Игрок попросил сделать сигналы такими же, как объекты: выбираемыми,
отключаемыми и — впоследствии — создаваемыми в редакторе.

## Решение

**Сигналы наблюдения становятся вторым видом правил внутри того же типа набора
`mapControl`.** К массиву `rules` добавляется массив `visionRules`.

Правило наблюдения описывается парой «роль соперника × событие» и содержит те же
поля представления, что и правило объекта:

```json
{
  "id": "enemy-jungler-appeared",
  "position": "jungle",
  "transition": "appeared",
  "priority": "caution",
  "message": "…",
  "whyNow": "…",
  "nextGoal": "…",
  "isEnabled": true
}
```

Формат поддерживает **всю матрицу** ролей и событий с первого дня. Поставляются
только два встроенных набора — лесник и мидер, — но правило для любой другой
роли выражается тем же файлом и работает без изменений в коде.

### Почему не отдельный тип набора

`mapAwareness` потребовал бы второго загрузчика, валидатора, библиотеки, импорта
и редактора. Игрок получил бы два списка вместо одного и был бы обязан понимать
разницу, которой для него нет: и то и другое — контроль карты.

### Почему не общий тип правила с объектами

Правило объекта запускается **игровым временем** и срабатывает заранее, с
упреждением `leadTime`. Сигнал наблюдения запускается **наблюдением** и
срабатывает по факту. Поля `objective`, `trigger` и `leadTime` для сигнала
бессмысленны, а `position` и `transition` бессмысленны для объекта. Один тип
правила означал бы половину полей, обязанных пустовать.

### Почему не галочки в настройках

Дёшево, но теряется всё, ради чего наборы и заведены: формулировка, «почему
сейчас», «что дальше», обмен наборами. Игрок просил «как для драконов», а не
«включить или выключить».

## Последствия

**Совместимость нарушается в одну сторону.** Набор с `visionRules`, сохранённый
новой версией, старая прочитает без этих правил и молча потеряет их. Обратно —
набор без `visionRules` читается новой версией как есть. Номер схемы не
повышается: массив необязательный, и его отсутствие — нормальное состояние.

**Код перестаёт знать, какие сигналы существуют.** `MapAwarenessSignalKind`
с двумя значениями исчезает; вместо него сопоставление наблюдения с правилами
включённых наборов. Текст берётся из правила, а не из строк локализации
приложения, — как и у объектов.

**Редактор правил наблюдения отложен.** Формат его допускает, но пошаговый
редактор для них появится позже, отдельной работой. До тех пор игрок
пользуется встроенными наборами и может править их копии как файлы.

**Порог уверенности остаётся в коде.** `MinimumOperationalConfidence` — свойство
распознавания, а не пожелание автора набора. Отдавать его в JSON значило бы
позволить набору включить заведомо ненадёжные наблюдения.
