# Architecture Decision Records

ADR фиксирует важное архитектурное решение и причину, по которой оно принято. Это помогает не возвращаться к уже решённому вопросу без нового контекста и не превращать архитектуру в набор устных договорённостей.

## Когда нужен ADR

- меняется направление зависимостей или ответственность проекта;
- добавляется внешний адаптер, хранилище либо production-зависимость;
- выбирается формат данных, влияющий на совместимость;
- принимается новый общий UI- или concurrency-паттерн;
- делается осознанное исключение из `docs/architecture.md`.

Локальный рефакторинг, исправление дефекта и реализация уже принятого правила ADR не требуют.

## Имя файла

```text
NNNN-short-title.md
```

Номер увеличивается последовательно: `0001`, `0002` и так далее. Заголовок файла — короткий, на английском; содержимое — на русском.

## Шаблон

```markdown
# NNNN. Название решения

- Статус: предложено | принято | заменено | отклонено
- Дата: YYYY-MM-DD

## Контекст

Какую проблему решаем, какие ограничения и силы влияют на решение?

## Решение

Что именно выбираем и где проходит новая граница?

## Альтернативы

Какие реалистичные варианты рассмотрены и почему не выбраны?

## Последствия

Что становится проще, что сложнее, какие риски и последующие действия появляются?
```

ADR не переписывается задним числом после изменения решения. Создай новый ADR и пометь прежний как заменённый.
